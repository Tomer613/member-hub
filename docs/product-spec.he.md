# פלטפורמת SaaS לניהול מנויים וקהילות – הגדרת פרויקט

Oct 7, 2026 · @Tommy

## חזון ומטרות

פלטפורמת SaaS אחת שמנהלת מנויים, חיובים וקשר עם חברים לכל סוג של קהילה או מועדון, וממשק שמתאים את עצמו לסוג הארגון שנבחר.

- **קהל יעד:** ועדי בית, קהילות ובתי כנסת, מועדונים, חדרי כושר וארגונים דומים, בישראל ובעולם.
- **הערך הייחודי:** ליבה גנרית אחת, ו"חבילה" לכל סוג ארגון שמביאה את המונחים, השדות והזרימות המדויקים שלו.
- **מודל עסקי:** הפלטפורמה גובה עמלה חודשית או שנתית מכל ארגון, ואפשר להוסיף אחוז מהתשלומים שעוברים דרכה.
- **מטרה ראשונה:** MVP עובד עם חבילה אחת, ואימות שחבילה שנייה נבנית בלי לשכתב את הליבה.

## עקרונות מוצר וארכיטקטורה

ליבה אחת משותפת לכל הארגונים, וחבילות תצורה שמתאימות אותה לכל סוג.

החבילות יושבות מעל הליבה ומשנות מינוח, שדות ומודולים בלבד. הליבה זהה לכולם, והארגונים מופרדים זה מזה ברמת מסד הנתונים.

## מודל נתונים ראשוני

כל טבלה שייכת לארגון (tenant), והשדות הייחודיים לכל סוג ארגון נשמרים כשדות מותאמים לפי הגדרת החבילה ולא כעמודות קבועות.

| ישות | מה היא מייצגת | דוגמאות לשימוש |
| --- | --- | --- |
| ארגון (Tenant) | הלקוח של הפלטפורמה, עם סוג, מדינה, מטבע ושפה | ועד בית ברחוב מסוים, בית כנסת, חדר כושר |
| משתמש ותפקיד | מי נכנס למערכת ומה מותר לו | מנהל, גבאי, גזבר, חבר, מאמן |
| חבר | אדם או יחידה שמשלמת ומקבלת שירות | דייר, מתפלל, מתאמן |
| קבוצה / משק בית | קישור בין כמה חברים ליחידה אחת | דירה, משפחה, מנוי משפחתי |
| תוכנית מנוי | מחיר, מחזוריות וכללים | דמי ועד חודשיים, מנוי שנתי, כרטיסיה |
| מנוי | חבר שמחובר לתוכנית, עם תאריכי התחלה וסיום | הקפאה, חידוש, ביטול |
| חיוב וחשבונית | סכום לתשלום ומסמך מס | חיוב חוזר, חוב פתוח, קבלה |
| תשלום | מימוש חיוב דרך ספק סליקה | כרטיס אשראי, הוראת קבע, מזומן שנרשם ידנית |
| אירוע | דבר שקורה בזמן ומשתתפים בו | אסיפה, שיעור, תפילה, כניסה למכון |
| שדה מותאם | שדה שהחבילה מגדירה לארגון | מספר דירה, תאריך יארצייט, סוג מנוי |

## חבילות לפי סוג ארגון

חבילה היא קובץ תצורה שמגדיר מינוח, שדות מותאמים, תוכניות מנוי מוכנות, דוחות ומודולים פעילים. בהרשמה הארגון בוחר סוג, והמערכת נפתחת כבר מותאמת.

| חבילה | מונחים | מודולים ייעודיים |
| --- | --- | --- |
| ועד בית | דייר, בעל דירה, דמי ועד | הוצאות ותקציב, בעלים מול דיירים, אסיפות והצבעות, תקלות ותחזוקה |
| בית כנסת | מתפלל, גבאי, עלייה | תרומות ונדרים, יארצייט ותאריך עברי, מקומות ישיבה לימים נוראים, לוח זמנים |
| חדר כושר | מתאמן, מאמן, כרטיסיה | כניסות ובקרת כניסה, הקפאת מנוי, שיעורים והזמנות |
| מועדון | חבר, ועדה, הטבה | אירועים והרשמה, רמות חברות, כרטיסים |

הליבה מכילה כל מה שמשותף לכולם: חברים, מנויים, חיובים, תקשורת ודוחות. מודול ייעודי נכנס לחבילה רק אם לפחות סוג ארגון אחד צריך אותו.

## תשלומים ועסקי הפלטפורמה

החלטה: הכסף עובר דרך הפלטפורמה, אבל הסליקה, אימות הזהות (KYC) והאחסון של פרטי כרטיס נשארים אצל ספק מורשה. הפלטפורמה לא נוגעת בנתוני כרטיס אשראי.

- **מודל תשלום:** ספק "פלטפורמה ותתי-חשבונות" (למשל Stripe Connect או שווה ערך) שמאפשר לכל ארגון לקבל כסף ישירות, ולפלטפורמה לגבות עמלה אוטומטית מכל עסקה.
- **דמי שימוש לפלטפורמה:** מנוי חודשי או שנתי לכל ארגון, מחושב לפי מספר חברים או לפי חבילה.
- **ישראל:** תמיכה בסולקים מקומיים (Cardcom, Tranzila, PayMe, Grow ואחרים), והפקת חשבונית או קבלה חוקית דרך ספק מורשה.
- **בינלאומי:** מטבע ושפה לכל ארגון, מע"מ ומסים לפי מדינה, וכללי חשבוניות שונים בכל שוק.

דברים שחובה לאמת לפני שמתחייבים לספק (הזמינות משתנה לפי מדינה, ואני לא בדקתי אותם עכשיו):

- האם הספק זמין לעסקים הרשומים בישראל, ואילו מדינות הוא מכסה.
- דרישות הקצאת מספר חשבונית של רשות המסים בישראל.
- האם מודל הפלטפורמה מחייב רישיון או רישום נוסף שלך כמפעיל.

## המלצת סטאק טכנולוגי

ההמלצה: סטאק אחד ב-TypeScript, מנוהל ברובו בשירותים מנוהלים, כדי שמפתח יחיד עם כלי AI יוכל להחזיק אותו.

| שכבה | המלצה | למה |
| --- | --- | --- |
| ממשק | Next.js עם React, Tailwind, ו-PWA | אתר ואפליקציה מאותו קוד, תמיכה טובה ב-RTL ובריבוי שפות |
| שרת | TypeScript (Next.js API או NestJS) | שפה אחת לכל המערכת, קל ל-AI לכתוב ולבדוק |
| מסד נתונים | PostgreSQL עם Row Level Security | הפרדה בין ארגונים ברמת המסד, לא רק בקוד |
| הזדהות | ספק מנוהל (Clerk, Auth0 או Supabase Auth) | אבטחה ואימות דו-שלבי בלי לבנות לבד |
| תשלומים | ספק פלטפורמה לפי הפרק הקודם | עמלות אוטומטיות ופחות אחריות רגולטורית |
| הודעות | מייל, SMS ו-WhatsApp דרך ספקים מורשים | מבוסס תבניות, נשלט לפי ארגון |
| בינלאומיות | ספריית i18n, מטבע ואזור זמן לכל ארגון | RTL ו-LTR מהיום הראשון |
| אפליקציות נייטיב | Capacitor או React Native, רק אחרי ה-PWA | מונע בנייה כפולה בשלב מוקדם |

הצעה זו היא נקודת פתיחה. אם יש לך כבר ניסיון או קוד בסטאק אחר בפרויקטים הקיימים, זה שיקול משמעותי ונתאים אליו.

## מפת דרכים ושלבים

הסדר מבטיח שהגנריות נבדקת מוקדם: אחרי שתי חבילות עובדות מעל אותה ליבה, כבר ברור אם הארכיטקטורה נכונה.

1. **שלב 0, הגדרה:** סקירת הקוד הקיים של ועד הבית ובית הכנסת, וסגירת ההחלטות הפתוחות.
2. **שלב 1, ליבה:** ארגונים, הרשאות, חברים, תוכניות מנוי, חיובים ותשלום ראשון דרך ספק סליקה.
3. **שלב 2, חבילה ראשונה (MVP):** ועד בית או בית כנסת, הראשון שהקוד הקיים שלו קרוב יותר לגמור.
4. **שלב 3, חבילה שנייה:** חבילה אחרת, כדי לבדוק שאין צורך לשכתב את הליבה.
5. **שלב 4, PWA ואפליקציות:** אפליקציית ווב מתקדמת לחברים ולמנהלים, ואחר כך נייטיב אם יש צורך.
6. **שלב 5, הרחבה:** חדרי כושר ומועדונים, בינלאומיות מלאה ועמלות פלטפורמה.

- **רגולציה:** העברת כסף וחשבוניות הן תחומים שבהם טעות עולה ביוקר. הפתרון: ספקים מורשים בלבד.
- **גנריות יתר:** ליבה שמנסה להתאים לכולם עלולה להיות מסורבלת. הפתרון: מודול נכנס לליבה רק אם שני סוגי ארגון לפחות צריכים אותו.
- **תלות במפתח יחיד:** אתה לבד על המערכת. הפתרון: בדיקות אוטומטיות ותיעוד כבר מההתחלה.

1. בסרגל הצד של Claude נכנסים ל-Projects ולוחצים על פרויקט חדש.
2. נותנים שם, למשל שם הפלטפורמה, ותיאור קצר.
3. בשדה ההוראות (Instructions) מדביקים את הטקסט שבהמשך.
4. מעלים את החומרים מהרשימה למטה לאזור הקבצים של הפרויקט (Project knowledge).

כללי עבודה:
- כתוב בעברית, קצר וענייני. קוד והערות טכניות באנגלית.
- לפני החלטה ארכיטקטונית: הצג 2-3 אפשרויות, יתרונות וחסרונות, והמלצה אחת.
